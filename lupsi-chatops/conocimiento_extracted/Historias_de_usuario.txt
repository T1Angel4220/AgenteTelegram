1.  Título
Definición formal de historias de usuario y trazabilidad por sprint para el Sistema
Web Progresivo LUPSI
2.  Introducción
Las historias de usuario constituyen una forma estructurada de expresar necesi-
dades funcionales desde la perspectiva de los actores que interactúan con el sistema.
En un proyecto ágil como LUPSI, este mecanismo permite organizar el trabajo por
valor de negocio, priorizar entregables y verificar de manera objetiva cuándo una
funcionalidad se considera completa.
El presente documento formaliza las historias de usuario del Sistema Web Progre-
sivo LUPSI y las vincula con su planificación por sprints. La versión actual incorpora
de forma explícita el Sprint 1 como base de ingeniería del producto, ya que en esa
etapa se establecen los requerimientos funcionales, el diseño de interfaces (UX/UI),
la arquitectura del sistema, el modelado relacional de la base de datos y la iniciali-
zación de repositorios. A partir del Sprint 2, se aborda la codificación del backend,
frontend, políticas de seguridad y validaciones como el algoritmo Módulo 10.
Este documento tiene un alcance descriptivo y funcional. Su finalidad es dejar
claramente establecidas las necesidades de los usuarios, las condiciones de aceptación
y la relación entre dichas necesidades y el backlog técnico del proyecto.
3.  Objetivo
Definir de manera clara y formal las historias de usuario del sistema LUPSI,
relacionándolas con los sprints de desarrollo y con los criterios de aceptación que
permitirán verificar su cumplimiento durante la construcción del producto.
4.  Definiciones
Historia de usuario: descripción breve de una necesidad funcional expresada
desde la perspectiva de un actor del sistema, acompañada de un resultado
esperado y criterios de aceptación.

5.  Historias de Usuario del Sistema LUPSI
5.1.  US-01: Registro y Validación Oficial
Rol: Paciente.
Descripción: Como paciente, quiero registrarme en el sistema validando mi docu-
mento de identidad para acceder de forma ágil.
Propósito funcional: Esta historia permite formalizar el acceso inicial del pa-
ciente al sistema mediante la validación de su identidad. Con ello se asegura que el
registro solo sea aceptado cuando el documento cumpla con el formato y la lógica
de verificación definida por el sistema.
Criterios de aceptación:
El sistema invoca correctamente el algoritmo Módulo 10 para la validación de
cédulas.
El sistema rechaza cédulas irregulares o inválidas.
La transacción de alta del usuario se persiste correctamente.
El sistema genera y entrega un JWT activo al completar el registro.
La interfaz PWA ofrece una experiencia fluida y sin fricción al usuario.

5.2.  US-02: Agendamiento de Citas Síncrono
Rol: Paciente.
Descripción: Como paciente, quiero visualizar los horarios médicos y reservar mi
cita sin demoras de autorización.
Propósito funcional: Esta historia habilita la reserva de citas médicas desde la
interfaz del paciente, garantizando que la información de disponibilidad se mantenga
consistente en tiempo real y evitando conflictos de agenda.
Criterios de aceptación:
El sistema deniega estrictamente la superposición de citas.
No se permite el doble agendamiento sobre un mismo horario.
La reserva se persiste automáticamente en la base de datos.
El horario ocupado deja de estar disponible para otros usuarios concurrentes.
5.3.  US-03: Visualización de Agenda Administrativa
Rol: Recepcionista.
Descripción: Como recepcionista, quiero previsualizar el calendario médico general
para conocer la carga diaria.
Propósito funcional: Esta historia permite al personal administrativo consul-
tar la agenda general sin comprometer la privacidad de los datos clínicos, facilitando
la organización operativa del centro médico.
Criterios de aceptación:
La agenda refleja en tiempo de ejecución los horarios reservados.
La vista presenta únicamente detalles primarios y demográficos.
El acceso respeta las restricciones de seguridad y no expone información clínica
sensible.
5.4.  US-04: Digitalización de Expedientes en Nube
Rol: Médico.
Descripción: Como médico, quiero subir recetas y reportes clínicos en formato
PDF asociado a mis pacientes.

5.5.  US-05: Restricción de Privacidad y Data Médica
Rol: Centro clínico.
Descripción: Como centro clínico, requiero que el sistema proteja a toda costa la
privacidad del paciente del personal de secretaría.
Propósito funcional: Esta historia establece las medidas de control de acceso
necesarias para proteger la información médica sensible, limitando el acceso según
rol y nivel de autorización.
Criterios de aceptación:
Se aplican políticas estrictas de acceso a nivel de base de datos.
Se respeta el modelo RLS y RBAC definido para el sistema.
Todo intento no autorizado desde un token del rol Recepcion hacia la tabla
Historias es rechazado con error 403 o 401.
La información clínica permanece restringida únicamente a los perfiles permi-
tidos.
6.  Backlog Técnico Habilitador del Sprint 1
El Sprint 1 no corresponde a una historia de usuario final, sino al conjunto de
tareas de análisis y arquitectura que hacen posible el desarrollo posterior del sistema
evitando reprocesos y deuda técnica.
Objetivo del Sprint 1: establecer el diseño visual, la arquitectura de software
y el modelado de la base de datos antes de iniciar la etapa de codificación.

9.  Conclusiones
Las historias de usuario constituyen la base funcional del sistema LUPSI, ya
que traducen las necesidades de los actores del negocio en requisitos concretos y
verificables. Su definición permite orientar el desarrollo hacia el valor real esperado
por el proyecto, al mismo tiempo que establece una guía clara para la construcción,
prueba y validación de cada incremento.
La incorporación explícita del Sprint 1 como fase de diseño y arquitectura permite
reconocer que, antes de la codificación, existe una etapa de análisis indispensable
que sostiene el producto. De esta forma, el documento refleja la madurez técnica del
equipo para avanzar de manera ordenada hacia la fase de desarrollo en el Sprint 2.
